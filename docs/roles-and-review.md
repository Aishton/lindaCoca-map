# 角色与权限设计：用户与管理员

> 状态：角色与权限约定。标「已实现」的是当前线上已有的能力，标「规划」的尚未实现。
> 部署、数据库迁移、账号管理等系统维护工作不在本文范围，见[项目整体维护方案](maintenance.md)。

网站只有两类使用者：**用户**和**管理员**。本文说明各自能做什么、不能做什么，以及这个边界靠什么保证。

## 两个角色

| 角色 | 是谁 | 需要登录 | 当前状态 |
| --- | --- | --- | --- |
| 用户 | 任何打开网站的人，无需注册 | 否 | 已存在 |
| 管理员 | 负责核验、采纳或驳回纠错的人 | 是（规划） | 尚未实现 |

当前没有登录系统，也没有管理员账号。位置纠错靠“用户导出 JSON → 维护者人工审核后改 `database/seed.json`”的离线流程完成，审核动作等于一次代码提交。这个流程只有一两个人时可用，多人提交后必须换成下面描述的在线审核。

## 能力对照

| 能力 | 用户 | 管理员 | 入口／落地位置 |
| --- | --- | --- | --- |
| 看推荐、按菜名筛选、换一家 | 已实现 | 已实现 | 首页 |
| 搜索地点、查看详情 | 已实现 | 已实现 | 搜索框、详情弹窗 |
| 地图浏览、缩放、食堂／店铺筛选 | 已实现 | 已实现 | 首页地图 |
| 在地图上圈点，生成位置纠错草稿 | 已实现（仅本地） | 已实现（仅本地） | 详情 → 纠错反馈 |
| 复制／下载校准 JSON | 已实现 | 已实现 | 纠错面板 |
| 提交纠错提案到服务端 | 规划 | 规划 | `POST /api/corrections` |
| 查询自己提案的状态 | 规划 | 规划 | 回执码，无需登录 |
| 查看待审核队列 | 禁止 | 规划 | `GET /api/admin/corrections` |
| 批准／驳回／要求补充 | 禁止 | 规划 | `POST /api/admin/corrections/:id/*` |
| 直接修改正式地点数据 | 禁止 | 仅通过审核动作 | — |
| 把地点标为「已确认」 | 禁止 | 规划，须填写依据 | 管理员审核页 |
| 管理管理员账号、部署、迁移、回滚 | 禁止 | 禁止（可另授） | 见「兼任与授权」 |

两条硬约束：

1. **用户永远不能直接写正式数据。** 任何提交都先落 `pending` 提案，只有管理员的审核动作能改 `places`。
2. **管理员也不能“顺手”改。** 修改必须走审核接口，并在同一事务里写审计日志；直接改库或直接编辑线上数据等于绕过追溯。

## 兼任与授权

四人小组里，同一位成员很可能既做内容审核又管部署。**允许兼任，但两项权限分开授予、分开留痕**：

- 授予的是**权限**，不是头衔。判断某人能不能做某件事，按上面能力对照表逐项看，不按“他是管理员”推断。
- 兼任时两道流程都不能省：审核动作照样进审计日志，部署照样走发布流程，不能因为“两样我都有权”就跳过其中一道。
- 授予与收回都要记录：谁在什么时候拿到了哪项权限；交接时逐项确认，见[项目整体维护方案](maintenance.md)的交接清单。
- 兼任不豁免自审限制：数据类改动仍然不能自己改自己审。

## 用户能做什么

### 现在

不需要账号，打开就能用：

- 午餐／晚餐场景标记、按菜名关键词筛选、“帮我决定今天吃什么”和“换一家”；
- 全部地点搜索与餐饮点详情；
- Leaflet + OpenStreetMap 校园地图的浏览、搜索、筛选和标记弹窗；
- 从详情进入“纠错反馈 → 在地图上重新圈位置”，草稿存在浏览器 `localStorage`（键名 `hustmap-calibration-draft-v2`）；
- 用“复制校准结果”或“下载 JSON”把草稿交给维护者。

圈点结果一律是「大致位置」，不会因为被采纳就自动变成「已确认」。当前草稿只在本机，没有跨设备同步，清除网站数据即丢失。

### 规划中

- 直接把提案提交到服务端，拿到一个回执码；
- 凭回执码查询处理进度（无需注册）；
- 管理员要求补充材料时，追加说明或凭证；
- 后续按需增加登录，用于查看历史提案和接收结果通知——**登录不作为提交的前提**，避免把轻量纠错挡在门外。

## 管理员能做什么

### 现在：没有账号，靠人工流程

管理员动作目前由维护者手工完成：收到校准 JSON → 核对地点与坐标来源 → 改 `database/seed.json` → 提 PR → 合并后 GitHub Pages 自动更新。虽然能保证“用户不直接改数据”，但没有提案记录、没有审核痕迹、也无法承载多人同时提交。

### 规划中

- 登录后台，看到待审核队列；
- 打开单条提案，对比原坐标与新坐标、查看移动距离、用户说明和凭证；
- 执行“批准为大致位置”“凭可靠依据批准为已确认”“驳回”“要求补充”四种动作；
- 驳回必须填写原因，要求补充必须说明缺什么；
- 查看同一地点近期的重复提案，合并处理；
- 查询审计日志，追溯每次正式数据变更的前后值、提案、操作者和时间。

管理员**不自动拥有**：管理管理员账号、部署、迁移数据库、回滚。这些属于系统维护权限，需要单独授予——由同一位成员兼任时也一样，权限分开发，动作分开留痕。

## 权限边界

边界必须由服务端保证，前端隐藏按钮不算数：

- 所有写接口先校验身份与角色，再校验提案状态是否允许该动作；
- 状态流转只认合法路径（见下文“提案状态”），不能从 `rejected` 直接跳到 `approved`；
- 批准接口在**一个事务**内完成：检查 `base_revision`、更新 `places`、更新提案状态、写审计日志，任一步失败整体回滚；
- 正式表 `places` 与提案表必须分离，前端不能持有任何直写 `places` 的路径；
- 用户侧只能看到自己的提案内容，看不到他人信息和内部审核备注。

## 审核流程

```text
用户填写纠错
  → 服务端校验与限流
  → 写入待审核提案（pending）
  → 管理员对比原值、新值、距离和凭证
  → 批准 / 驳回 / 要求补充
  → 批准时用事务更新正式地点并写审计日志
  → 用户凭回执码查看结果
```

## 提案状态

| 状态 | 含义 | 谁能触发 |
| --- | --- | --- |
| `pending` | 等待审核 | 系统（提交时） |
| `needs_info` | 管理员要求补充说明或凭证 | 管理员 |
| `approved` | 已批准并成功写入正式数据 | 管理员 |
| `rejected` | 不采纳，必须保留原因 | 管理员 |
| `withdrawn` | 提交者主动撤回 | 用户（登录上线后） |

`approved` 与 `rejected` 是终态，重新提交应新建提案，不在原记录上反复改状态。

## 数据模型建议

现有 `feedback` 表可在原型阶段继续使用；进入多人提交后，建议扩展或迁移为结构化的 `correction_proposals`：

| 字段 | 用途 |
| --- | --- |
| `id`、`place_id` | 提案 ID 和目标地点 |
| `correction_type` | `position`、`name`、`hours`、`menu`、`closure` 等 |
| `payload_json` | 新坐标或其它拟议值 |
| `reason` | 用户说明 |
| `evidence_url` | 可选截图或来源链接 |
| `submitter_id` | 第一阶段可为空，登录上线后关联用户 |
| `status` | 审核状态 |
| `base_revision` | 提交时的地点版本，防止覆盖较新的修改 |
| `receipt_code` | 匿名提交的查询回执 |
| `reviewed_by`、`reviewed_at` | 审核人和时间 |
| `review_note` | 批准依据或驳回原因 |

另需不可变的 `place_change_log`，保存地点修改前后值、提案 ID、操作者和时间，用于追踪与回滚。

## API 草案

### 用户接口

- `POST /api/corrections`：提交纠错，返回回执码。
- `GET /api/corrections/:id`：凭回执码查看状态。
- `POST /api/corrections/:id/messages`：后期补充材料。

### 管理员接口

- `GET /api/admin/corrections?status=pending`：待审核队列。
- `GET /api/admin/corrections/:id`：查看原值、新值、历史提案。
- `POST /api/admin/corrections/:id/approve`：批准并更新正式数据。
- `POST /api/admin/corrections/:id/reject`：驳回并记录原因。
- `POST /api/admin/corrections/:id/request-info`：要求补充信息。

## 管理员审核页

位置纠错至少展示：

- 地点名称、现有状态和坐标来源；
- 原坐标与新坐标的并排地图；
- 两点移动距离；
- 用户说明和可选凭证；
- 同一地点近期的重复提案；
- “批准为大致位置”“凭可靠依据批准为已确认”“驳回”“要求补充”动作。

“批准为已确认”必须填写依据；普通人工圈点只能批准为「大致位置」。

## 安全与滥用防护

匿名提交必须在服务端做以下限制：

- 按 IP 或匿名客户端标识限流，不长期保存原始 IP；
- 校验坐标是否落在允许的校园范围内；
- 限制文本长度、文件类型和上传大小；
- 对输出做转义，防止脚本注入；
- 合并同地点、相近坐标的重复提案；
- 所有公开提交默认进入 `pending`，永不自动写入正式数据。

管理员会话需要独立的登录凭据与失效策略，不复用用户侧任何令牌。

## 建议实施顺序

1. 扩展提案表和审计日志表。
2. 实现公开提交接口、校验、限流和回执码。
3. 实现管理员登录和待审核列表。
4. 实现批准／驳回事务和地点版本检查。
5. 把现有浏览器 JSON 草稿改为提交接口。
6. 部署可写后端与持久数据库。
7. 按实际需要再考虑用户登录、通知与信誉机制。
