# 角色、权限与纠错审核设计

> 状态：规划文档。本文描述后续实现建议，不代表当前网站已经具备登录、提交或管理员审核功能。

## 设计目标

- 用户只能提交纠错提案，不能直接修改正式地点数据。
- 管理员可以核验、批准、驳回或要求补充信息。
- 每次正式修改都可追溯到提案、审核人和修改前后的值。
- 第一阶段尽量少做账号系统，先跑通提交和审核闭环。
- 人工圈点默认仍是“大致位置”，不能因为审核通过就自动变成“已确认”。

## 建议角色

| 角色 | 第一阶段 | 后续职责 |
| --- | --- | --- |
| 游客 | 浏览、筛选、查看详情；匿名提交纠错 | 保持公开只读 |
| 贡献者 | 暂不要求登录 | 登录后查看自己的提案、补充材料和接收审核结果 |
| 管理员 | 登录后台，审核纠错提案 | 管理地点、菜品、反馈和低风险内容修订 |
| 维护者 | 管理部署、数据库和管理员账号 | 处理权限、回滚、数据迁移与安全事件 |

管理员与维护者应分开：内容审核不应自动获得部署密钥、数据库迁移或账号管理权限。

## 权限边界

| 操作 | 游客／贡献者 | 管理员 | 维护者 |
| --- | --- | --- | --- |
| 查看公开地点 | 允许 | 允许 | 允许 |
| 提交纠错提案 | 允许 | 允许 | 允许 |
| 修改正式地点 | 禁止 | 仅通过审核动作 | 允许但必须留审计记录 |
| 批准或驳回提案 | 禁止 | 允许 | 允许 |
| 管理管理员账号 | 禁止 | 禁止 | 允许 |
| 部署、迁移和回滚 | 禁止 | 禁止 | 允许 |

## 推荐审核流程

```text
用户填写纠错
  → 服务端校验与限流
  → 写入待审核提案
  → 管理员对比原值、新值、距离和凭证
  → 批准 / 驳回 / 要求补充
  → 批准时用事务更新正式地点并写审计日志
  → 用户可查看结果或收到通知
```

正式地点表 `places` 和用户提案必须分离。不要让前端直接向 `places` 写入坐标。

## 提案状态

- `pending`：等待审核。
- `needs_info`：管理员要求补充说明或凭证。
- `approved`：已批准并成功写入正式数据。
- `rejected`：不采纳，必须保留原因。
- `withdrawn`：提交者主动撤回，可在用户体系上线后加入。

状态变化必须由服务端检查，不能只依赖前端隐藏按钮。

## 数据模型建议

现有 `feedback` 表可在原型阶段继续使用；进入多人提交后，建议扩展或迁移为结构化的 `correction_proposals`：

| 字段 | 用途 |
| --- | --- |
| `id`、`place_id` | 提案 ID 和目标地点 |
| `correction_type` | `position`、`name`、`hours`、`menu`、`closure` 等 |
| `payload_json` | 新坐标或其它拟议值 |
| `reason` | 用户说明 |
| `evidence_url` | 可选截图或来源链接 |
| `submitter_id` | 第一阶段可为空，登录上线后关联用户 |
| `status` | 审核状态 |
| `base_revision` | 提交时的地点版本，防止覆盖较新的修改 |
| `reviewed_by`、`reviewed_at` | 审核人和时间 |
| `review_note` | 批准依据或驳回原因 |

还应增加不可变的 `place_change_log`，保存地点修改前后值、提案 ID、操作者和时间，用于追踪与回滚。

## API 草案

### 公开接口

- `POST /api/corrections`：提交纠错。
- `GET /api/corrections/:id`：使用提交回执或登录身份查看状态。
- `POST /api/corrections/:id/messages`：后期补充材料。

### 管理接口

- `GET /api/admin/corrections?status=pending`：待审核队列。
- `GET /api/admin/corrections/:id`：查看原值、新值和历史提案。
- `POST /api/admin/corrections/:id/approve`：批准并更新正式数据。
- `POST /api/admin/corrections/:id/reject`：驳回并记录原因。
- `POST /api/admin/corrections/:id/request-info`：要求补充信息。

批准接口必须在数据库事务中同时完成：检查版本、更新地点、更新提案状态、写入审计日志。任一步失败都应整体回滚。

## 管理员审核页

位置纠错至少展示：

- 地点名称、现有状态和坐标来源；
- 原坐标与新坐标的并排地图；
- 两点移动距离；
- 用户说明和可选凭证；
- 同一地点近期的重复提案；
- “批准为大致位置”“凭可靠依据批准为已确认”“驳回”“要求补充”动作。

“批准为已确认”应要求填写依据，普通人工圈点只能批准为“大致位置”。

## 第一阶段可以不做普通用户登录

最小版本只需要管理员登录。匿名提交可以返回随机回执码，让提交者查询状态。为降低滥用风险，需要：

- 按 IP 或匿名客户端标识限流，不长期保存原始 IP；
- 校验坐标是否在允许的校园范围内；
- 限制文本长度、文件类型和上传大小；
- 对输出进行转义，防止脚本注入；
- 合并同地点、相近坐标的重复提案；
- 所有公开提交默认进入 `pending`，永不自动写入正式数据。

## 后续用户体系

当确实需要贡献记录、追问和通知时，再增加用户登录：

- 用户查看自己的提案和审核记录；
- 管理员请求补充材料；
- 用户收到批准或驳回通知；
- 记录贡献次数，但不要只凭次数自动授予修改权限；
- 删除账号时保留去身份化审计记录，避免破坏历史追踪。

## 部署影响

GitHub Pages 只能继续承载静态前端。正式提交和审核需要一个可写的后端 API、持久数据库以及安全的管理员会话。当前本地 SQLite 可以用于开发，但多人线上环境应使用有备份、事务和迁移能力的持久数据库。

## 建议实施顺序

1. 扩展提案表和审计日志表。
2. 实现公开提交 API、校验、限流和回执码。
3. 实现管理员登录和待审核列表。
4. 实现批准／驳回事务和地点版本检查。
5. 将现有浏览器 JSON 草稿改为提交 API。
6. 部署可写后端与持久数据库。
7. 根据实际需要再增加普通用户登录、通知和信誉机制。
