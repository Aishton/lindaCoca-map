# 项目整体维护方案

> 状态：维护约定 + 规划。文中标「规划」的部分尚未实现，不要当成现有能力。
> 相关的网站角色（用户能做什么、管理员能做什么）见[角色与权限设计](roles-and-review.md)。

本文回答四件事：谁维护、维护什么、多久维护一次、出问题怎么办。

## 维护对象

| 对象 | 位置 | 唯一真源 | 维护方式 | 主要风险 |
| --- | --- | --- | --- | --- |
| 网页前端 | `index.html`、`app.js` | 仓库 `main` 分支 | 分支 + PR | 直接改 `main` 会立刻影响线上 |
| 地点与菜品数据 | `database/seed.json` | 该文件本身 | 编辑 JSON + PR | 手改坐标或 ID 冲突 |
| 本地数据库 | `database/meishi.sqlite` | 由 `seed.json` 派生 | `node database/init.mjs` 重建 | 已列入 `.gitignore`，不可作为真源 |
| 只读后端 | `server/` | 仓库 `main` 分支 | 分支 + PR + 本地测试 | 接口字段与前端不一致 |
| 文档 | `README.md`、`docs/` | 仓库 `main` 分支 | 与代码同一次 PR | 文档描述落后于实现 |
| 线上站点 | GitHub Pages | `main` 分支的内容 | 合并即发布 | 没有暂存环境，合并即对外 |

关键结论：**`database/seed.json` 是唯一的线上数据源**。GitHub Pages 无法运行 Node.js，线上页面读的就是这个文件；`meishi.sqlite` 只是每位成员本地的派生物，丢了重跑初始化即可，不需要备份。

## 团队角色与分工

四人协作，一人可兼多职，但每个角色都要有明确的备份人。

| 角色 | 职责 | 当前承担人 | 备份人 |
| --- | --- | --- | --- |
| 项目负责人 | 排期、对外沟通、PR 最终合并决定、需求取舍 | 待组内确认 | 待组内确认 |
| 前端与交互 | `index.html`、`app.js`、地图与校准交互、页面验收 | 待组内确认 | 待组内确认 |
| 数据与地图坐标 | `seed.json` 准确性、坐标来源与状态判定、数据核对 | 待组内确认 | 待组内确认 |
| 后端与部署 | `server/`、`database/` 脚本、GitHub Pages 与后续可写后端 | 待组内确认 | 待组内确认 |
| 文档与交接 | 文档同步、PR 描述质量、结课归档 | 待组内确认 | 待组内确认 |

> 上表按仓库现有分工空出，请组内填写实际姓名后删除本行说明。

角色边界沿用[权限边界](roles-and-review.md#权限边界)中「管理员不做系统维护」的原则：审核内容的人不自动获得部署与数据库权限。本节讲的是团队维护职责，不是网站角色。

## 变更类型与审核关系

| 变更类型 | 提议 | 执行 | 审核（至少一人） | 告知 |
| --- | --- | --- | --- | --- |
| 文档与说明 | 任何人 | 提议人 | 项目负责人 | — |
| 前端交互与样式 | 任何人 | 前端 | 项目负责人 | 全组 |
| 地点／菜品数据 | 任何人 | 数据维护 | 数据维护以外的成员 | 全组 |
| 校准坐标落地 | 任何提交者 | 数据维护 | 数据维护以外的成员 | 全组 |
| 后端接口与脚本 | 任何人 | 后端 | 项目负责人 | 全组 |
| 部署相关配置 | 任何人 | 后端与部署 | 项目负责人 | 全组 |

数据类改动不允许自己改自己审：坐标和状态判定容易出错，必须有第二个人看过。

## 维护分级与响应

课程项目没有值班机制，响应时限按“能在下一次组会前处理完”设定。

| 级别 | 判定 | 例子 | 目标响应 |
| --- | --- | --- | --- |
| P0 | 线上不可用或数据被破坏 | Pages 白屏、`seed.json` 损坏导致全部地点消失 | 当天，先回滚再排查 |
| P1 | 主要功能失效 | 地图不加载、推荐或搜索报错、API 全 500 | 48 小时内 |
| P2 | 局部数据或功能错误 | 单个坐标明显偏移、菜品张冠李戴、筛选漏项 | 一周内 |
| P3 | 体验与文档问题 | 文案、排版、文档过期 | 下次迭代 |

判定原则：宁可先按高一级处理，回滚成本远低于线上出错。

## 日常维护（每次改动）

1. 同步 `main`：`git switch main && git pull origin main`。
2. 建主题分支：`git switch -c feat/short-description`（或用 `fix/`、`docs/`、`data/` 前缀）。
3. 只改一个主题，顺带更新对应文档与 `README.md` 的功能摘要。
4. 本地跑质量门禁，见下节。
5. 推送并开 PR，PR 描述写清「改了什么、为什么、怎么验证的」。
6. 至少一人 review 后合并；合并后立刻在线上页面按发布检查清单点一遍。

## 数据维护与恢复

### 日常数据改动

仅改 `seed.json`，不要直接改 `meishi.sqlite`：该文件被 `.gitignore` 排除，手工改动不会被他人继承，也不会进入线上。

```powershell
node database/init.mjs
node --check app.js
node --test server/app.test.mjs
```

`init.mjs` 按 `id` 插入或更新，可重复执行；但**从 `seed.json` 删掉一条记录，不会删除本地库里已存在的旧记录**。需要彻底重建时删除 `database/meishi.sqlite` 后重新运行 `node database/init.mjs`。

### 备份与回滚

- 备份就是 Git 历史：`seed.json` 的每次改动都有提交记录，不需要额外备份文件。
- 单个数据改动出错：`git revert <commit>` 后推送，Pages 自动回到上一版。
- 整批数据被破坏：`git checkout <上一个正常提交> -- database/seed.json`，提交后推送。
- 恢复后必须重新运行 `node database/init.mjs`，并核对线上页面。
- 「规划」：接入可写后端后，线上数据库需要独立的定期备份与恢复演练，Git 历史不再能覆盖这部分数据。

### 坐标与状态

维护坐标时以[地图与位置数据](map/README.md#位置状态规则)为准。人工圈点一律保持「大致位置」，审核通过也不自动升级为「已确认」；只有官方图层、现场核验或可追溯的可靠资料才能标记「已确认」。

## 版本与发布

- 默认分支为 `main`，所有改动经 PR 合入，禁止直接推送 `main`。
- 分支命名：`feat/`、`fix/`、`docs/`、`data/` + 简短英文描述。
- 提交信息一句话说清改动，例如 `Add overall maintenance plan`。
- PR 要求：至少一人 review；涉及数据或坐标时由非作者审核。
- 发布即合并：GitHub Pages 直接部署 `main`，没有暂存环境——合并前本地必须验证过。
- 回滚以 `git revert` 为主，不使用强制推送。
- 「规划」：按学期打 tag（如 `v2026-fall`）作为可回溯的发布点，并附一份简短更新说明。

## 质量门禁

合并前必须全部通过：

```powershell
node --check app.js
node --test server/app.test.mjs
node database/init.mjs
```

人工检查按[地图与位置数据](map/README.md#发布前检查)的发布前清单执行，并补充：

- 推荐、换一家、搜索、详情、地图筛选、合并标记、纠错入口可用；
- 校准 JSON 导出包含新旧坐标与地点 ID；
- 人工圈点仍显示虚线「大致位置」样式；
- `README.md` 的功能描述与实际一致；
- 新增文档已加入 `docs/README.md` 导航。

## 监控与告警

现状：没有监控，依靠每周人工冒烟。

「规划」低成本方案，按投入顺序：

1. 用 `GET /api/health` 做本地与部署后探活，部署脚本里先请求一次再放行。
2. 用 GitHub Actions 定时（每日）请求线上页面与 `database/seed.json`，检查 HTTP 200 与关键字段存在。
3. 接入可写后端后，再考虑错误日志、慢查询与磁盘告警，并明确告警接收人。

课程阶段不做 7×24 值班，允许故障在下次使用或冒烟时被发现，但发现后必须按分级响应。

## 事故处理

```text
发现异常
  → 定级（P0～P3）
  → P0/P1 先止损：回滚到上一个正常提交
  → 记录现象、时间、影响范围
  → 定位原因（对照最近合并的 PR）
  → 修复并补测试
  → 简短复盘：为什么没被发现，补哪一条检查
```

原则：先恢复可用，再查根因；不要在线上故障进行中顺手重构。

「规划」：在 GitHub Issues 中建立 `incident` 标签，复盘结论追加到本文档末尾的事故记录表。

## 文档维护与交接

- 未实现的设计必须标记「规划」，不得写成现有功能（沿用 `docs/README.md` 的既有约定）。
- 功能或使用方式变化时，同一次 PR 内更新对应专题文档与根目录 `README.md`。
- 地点来源、确认状态、人工圈点规则以 `docs/map/README.md` 为准；角色与权限以 `docs/roles-and-review.md` 为准；本文档只管维护流程，不重复定义业务规则。

交接清单（学期末或成员退出时逐项确认）：

- [ ] `seed.json` 与线上一致，本地初始化可复现
- [ ] 线上站点按发布检查清单通过
- [ ] 角色分工表、备份人已更新
- [ ] 未完成的规划项已写入本文档或 Issue
- [ ] 仓库权限、Pages 配置、凭据持有人已确认交接

## 风险登记

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 直接推送 `main` 导致线上故障 | P0 | 分支保护 + PR 审核；发现后立即 revert |
| `seed.json` 手工编辑引入语法错误 | 线上全部数据加载失败 | 合并前 `node database/init.mjs` 与页面自测 |
| 坐标被误标为「已确认」 | 误导用户，违背数据规则 | 数据改动由非作者审核；状态判定以地图文档为准 |
| 文档长期不更新 | 交接成本上升，新成员误用 | 文档随 PR 同步；每月检查 |
| GitHub Pages 无暂存环境 | 合并即对外 | 合并前本地完整验证；保留可回滚提交 |
| 后续可写后端缺少备份 | 数据不可恢复 | 上后端前先定备份与恢复演练方案 |
| 组员离开且无交接 | 维护中断 | 每角色设备份人；学期末交接清单 |

## 实施顺序

与[角色与权限设计](roles-and-review.md#建议实施顺序)对齐，维护侧先做不需要新基础设施的部分：

1. 填写角色分工表与备份人（本文档）。
2. 启用 `main` 分支保护，强制 PR 与至少一人审核。
3. 把发布检查清单固化为 PR 模板与本地检查脚本。
4. 「规划」按学期打 tag 并写简短更新说明。
5. 「规划」加入每日 Actions 可用性检查。
6. 接入可写后端前，先落地数据库备份与恢复演练方案。
